Every reason string in the log to the right is real: copied verbatim from
`src/pass-cli/install.sh`, the script that generates the `color` bin used
throughout this repo's own `pass-cli` test scenarios. Nothing here was
authored to resolve cleanly.

**The claim this lesson demonstrates is not "here is a log viewer."** It's
that an agent's stated reason can be type-checked against what it was
actually permitted to do -- the same `Diagnostic{severity, code, message}`
shape [CIT-139](https://github.com/null-hype/agent-plugins/tree/main/capability-spike)
already uses for `pkl/Ledger.pkl`'s `CAP_NO_GRANT`, `CAP_REJECTED`, and
`CAP_VAULT_MISMATCH`, extended one step earlier: from "may this fact
acquire the capability" to "does this fact's stated reason even name
something the supervisor recognizes."

## Right now, all three lines are underlined

`governedVocabulary.json` and `grantState.json` both start empty. Nothing
has been admitted, nothing has been granted, so all three reasons in the
log resolve to `CAP_TERM_UNRESOLVED` -- the one new code this lesson adds
alongside `Ledger.pkl`'s existing three. Open the log, hover any line: the
raw statement, its (empty) loss annotations, and the diagnostic are all
there, even though nothing has resolved to anything yet.

## The cycle: edit vocabulary/grant state, rerun, watch the markers respond

This is not a fixed recording. `governedVocabulary.json` is modelled on
chapter-1 lesson-2's `PersonalVocabulary.pkl`, with ownership inverted --
`pkl/GovernedVocabulary.pkl` (read-only, in the tree to the left) is the
real, supervisor-owned admitted list; `governedVocabulary.json` is your
editable copy of the same shape, starting empty. `grantState.json` mirrors
`pkl/GrantState.pkl` and chapter-3 lesson-2's own `grantState.json` the
same way. Every time either file changes, `ReasonResolverBridge` above
reruns `resolveReason` for all three lines and pushes the result straight
into the Monaco preview -- no page reload.

Walk the cycle on `"jin-91-resume-session scenario: planting codeword in a
fresh session"` (the log's middle line):

1. **Right now:** unadmitted -> `CAP_TERM_UNRESOLVED`.
2. **Copy its entry** from `pkl/GovernedVocabulary.pkl` into
   `governedVocabulary.json` (as a one-element array) and save. The line's
   diagnostic changes to `CAP_NO_GRANT` -- its meaning is resolved now, but
   **admission does not confer access**. `resolvedFactId` is populated;
   the check still fails, with a different code than before.
3. **Add a matching grant** to `grantState.json`'s `approvedGrants` --
   `{"pass-cli:color:resume:plant-codeword": {"factID": "...", "vault":
   "jin-91-resume-session", "approved": true}}` -- and the line clears
   entirely: no diagnostic, no underline.
4. **Now break it two different ways** and watch the codes stay
   distinguishable: flip `approved` to `false` (`CAP_REJECTED`), or leave
   it `true` but change `vault` to anything else (`CAP_VAULT_MISMATCH`).
   Neither collides with `CAP_NO_GRANT` or with each other.

**Admit + approve as supervisor** below the file tree jumps straight to
the fully-solved end state (both files' real, committed target contents)
if you'd rather see the destination first and work backwards. **Revoke**
puts both back to empty.

## Reused, not reinvented

[`reasonResolver.ts`](https://github.com/null-hype/null-hype.github.io/blob/main/tutorial-app/src/lib/reasonResolver.ts)'s
`resolveReason` is unchanged by any of this -- same function chapter-3
lesson-2/3 already trust,
[typed against](https://github.com/null-hype/null-hype.github.io/blob/main/tutorial-app/src/lib/governedVocabulary.pkl.ts)
the generated `AdmittedTerm`/`Grant` shapes, reusing
[`ledgerCheckAccess.ts`](https://github.com/null-hype/null-hype.github.io/blob/main/tutorial-app/src/lib/ledgerCheckAccess.ts)'s
`CAP_NO_GRANT`/`CAP_REJECTED`/`CAP_VAULT_MISMATCH` exactly. `resolveReasonLog`
is the only new piece: it parses your two live files into that same typed
shape and calls `resolveReason` three times, once per line.

## Rendered in the editor surface that already exists

The preview on the right is the same `otel-warm-log` Monaco template
chapter 1 uses for its warm-log traces. That template already registered a
Monarch tokenizer and a folding provider; this lesson is what adds
`setModelMarkers` (the underline) and `registerHoverProvider` (the
message, for every line, not only a failing one). No new file format, no
OTLP ingest, no peek-to-definition.

**Supporting files**, all real, in the tree to the left:
`pkl/GovernedVocabulary.pkl` (the admitted vocabulary) and `pkl/Ledger.pkl`
+ `pkl/GrantState.pkl` (the capability gate, unchanged from CIT-139), plus
the TypeScript replays this browser lesson runs instead of a live Pkl
evaluator -- `reasonResolver.ts`, `ledgerCheckAccess.ts`, and the fixtures
themselves in `reasonFixture.ts`.
